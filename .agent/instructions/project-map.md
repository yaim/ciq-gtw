Sections 9.5 and 25 own the OpenCode session-title extension endpoint and the OpenCode plugin / native-title propagation behavior.

**Implemented (upstream boundary, offline Phase 0):** `src/collectiviq/` — the production adapter (`adapter.ts`), bounded transport (`http.ts`, including the discovery-only any-status `observeUpstreamJson` that is not exported from `index.ts`), shared pure request builders (`requests.ts`), provisional response validators (`validation.ts`), normalized error model (`errors.ts`), fixed endpoint paths (`endpoints.ts`), adapter types/capabilities (`types.ts`), value-free correlation (`correlation.ts`), and the opt-in **staged discovery session** plus SSE evidence and sanitized structural capture (`discovery.ts` — `DiscoverySessionRunner`, `readSseEvidence`, strict `exitCodeForBaseline`; thin `discovery-cli.ts`; `structural-capture.ts`). Discovery captures raw upstream structure, retains correlation ids privately, keeps a truthful cleanup ledger, and gates every destructive delete on approval. The filtered OpenAPI snapshot lives at `contract/collectiviq/`, its tooling at `scripts/openapi/`, and hermetic contract tests at `test/contract/`. **The production adapter is now wired into the Phase 1B completion path** (`POST /v1/chat/completions`; see the Phase 1B entry below). The discovery, recovery, SSE-evidence, and other operator tooling remain out-of-band and are not public production routes. Construction and import stay socket-free and perform no upstream I/O; only a real completion request reaches CollectivIQ.

**Implemented (Phase 1B non-streamed chat completions, offline):** `src/api/chat-completions-route.ts` (the authenticated `POST /v1/chat/completions` route, its child-scope framework-error mapping, and client-disconnect wiring), `src/openai/chat-types.ts`/`messages.ts`/`chat-request.ts` (request validation/normalization) and `chat-response.ts` (the non-streamed encoder), `src/prompts/conversation.ts` (protocol-mode full-history versioned serializer), `src/prompts/direct.ts` (direct-mode latest-user-only serializer), `src/prompts/serializer.ts` (the model-policy-aware router that dispatches on the resolved model's validated `promptMode` — never a model-id string — with `protocol` the backward-compatible default and `direct` intentionally lossy, limited to the latest normalized user message), `src/generation/types.ts` (capacity/poller/serializer ports), `capacity.ts` (global + per-key active admission with a bounded queue — PROCESS-LOCAL, and the whole of admission control unless the optional Phase 4D layer below is explicitly enabled), `polling.ts` (bounded polling + desired-source selection), `chat-completion.ts` (orchestration), `seams.ts` (clock/id), and `runtime.ts` (composition from validated config). The `ModelCatalog` now also resolves the internal `VirtualModel` policy (`resolveModel`) without changing public model output. `validateChatRequest` takes that resolver, returns the resolved `VirtualModel` alongside the frozen request, and runs the model-policy-aware **tool-metadata compatibility bridge (Phase 2.1)**: for a `toolMode: "disabled"` model it tolerates and discards OpenCode's automatic `tools`/`tool_choice` metadata (bounded to ≤128 entries AND ≤2 MiB aggregate JSON via a descriptor-only, iterative shape/byte accounting that never invokes `[[Get]]`/getters/`toJSON`; retained/serialized/forwarded nowhere) and rejects required/named choices and malformed/over-budget collections; a `native` model is unimplemented, so any tool metadata is rejected. A `toolMode: "emulated"` model instead normalizes and retains the tool policy (owned by the Phase 3 inventory below). The raw-body access and tool-name recording stay inside the `src/openai/` boundary. The CollectivIQ adapter is now wired into this completion path (one new thread per request by default; the optional off-by-default Phase 5A reuse inventory below is the single exception); construction still makes no upstream call.

**Implemented (Phase 2 text-only synthetic SSE streaming, offline):** `src/openai/chat-stream.ts` (the pure `chat.completion.chunk` frame encoders and the deterministic, code-point-safe content split — the OpenAI boundary owns frame encoding and splitting) and `src/api/chat-stream-response.ts` (the SSE transport — header commit after preparation, backpressure-aware serialized writes, keep-alive timers, terminal/`[DONE]` framing, content-free error records, and write-failure/disconnect cancellation — the API boundary owns SSE transport, backpressure, keep-alives, and cancellation). The same `POST /v1/chat/completions` route serves both paths; `chat-completion.ts` is split into a synchronous `prepare` and an async `run` so the API layer commits SSE headers only after preparation succeeds. `chat-request.ts`/`chat-types.ts` normalize `stream` to a boolean.

**Implemented (native-title propagation; spec §§9.5 and 25):** `src/api/opencode-title-route.ts` owns the authenticated `GET /v1/opencode/session-title` route — a CollectivIQ/OpenCode **extension**, not part of the OpenAI profile. `src/opencode/title-bridge.ts` owns the bounded, process-local correlation from `gatewayKeyId + sessionId` to the upstream thread id (never a title/prompt/answer; TTL 60 s, caps 128/32). `.opencode/plugins/collectiviq-native-title.ts` is the dependency-free OpenCode plugin that best-effort renames the OpenCode session from the CollectivIQ provider-native title via that extension endpoint. Its `chat.headers` hook has **two independent responsibilities behind one shared gate** (exact `collectiviq-text` agent + `collectiviq` provider + a session id the gateway would accept): it attaches `X-CollectivIQ-OpenCode-Session-ID` to **every** matching request — synchronously, before any title work, because optional thread reuse (spec §5.1.1) needs the identity on every turn — and it arms **one** native-title workflow while the session's bounded state entry is retained. Do not re-couple them: a manual/renamed/already-propagated/child session or a failed or timed-out metadata lookup keeps the header and arms nothing, while an invalid session id or a different agent/provider gets no header and does not consume the session's pending arming opportunity. That title state is a bounded 256-entry INSERTION-ORDER map (not an LRU: it evicts the oldest inserted retained entry and access does not refresh insertion order), so repeated and concurrent requests do not rearm a retained entry, but eviction may permit a later workflow — updated non-default metadata blocks rearming while stale cached default metadata may permit one more bounded arm+poll, and the overwrite guarantee comes from the rename-side current-title recheck before `session.update`, not from the arming gate. Write the scoped form, never "at most once per session", never "LRU"/"most recent sessions", and never "a changed title makes a restart impossible". Keep three bounded stores distinct: the gateway correlation registry (gateway process, 60 s TTL, 32-per-key/128-global caps), the plugin's `sessions` title state, and the plugin's separate `metaCache` (both OpenCode-process, 256-entry insertion-order, no time-based expiry); none bounds another. The plugin's entry module **default-exports the OpenCode V1 `{ id, server }` plugin object** so OpenCode 1.18.21's loader invokes only `default.server` and never scans the module's named runtime exports. Its provider match reads own data-property descriptors only and fails closed: it accepts the flat runtime `provider.id` as authoritative and falls back to the nested SDK `provider.info.id` only when the flat property is absent (offline hardening). Global and project-local discovery share **one** process-wide hooks/state instance through a `Symbol.for(...)`/`globalThis` singleton (first initialization wins). OpenCode's hidden LLM `title` agent stays disabled in the committed `opencode.jsonc`, so propagation adds no separate completion/thread. The **historical 2026-08-21 sequence** was: the plugin entry module never loaded — its earlier bare-function default was rejected by OpenCode's legacy export scan (`Plugin export is not a function`) — so provider matching, header attachment, polling, and rename never ran (the flat/nested provider support was not that live cause); then, after the V1 default-module loader fix, a trace showed the poller stop before its first title lookup because it resolved its key only from `process.env.COLLECTIVIQ_GATEWAY_KEY` (absent). Both are fixed: the plugin default-exports the V1 module, and it performs one bounded, descriptor-safe connection resolution that reuses the resolved CollectivIQ provider `options.apiKey` (merged-over-embedded) with `COLLECTIVIQ_GATEWAY_KEY` as a lazy fallback, keeping the key local to the poll (never stored/logged). The provider-config→environment precedence and the lazy env fallback are hermetically verified. A sanitized, user-authorized **2026-08-22 live smoke observed the complete propagation path succeed for the tested local configuration** (OpenCode 1.18.21): exactly one new foreground CollectivIQ thread, no hidden title thread, a provider-native title generated for that thread, and the OpenCode top-level session title changed from its default to that provider-native title (the foreground response completed and was relevant, with no alert/tool call). This is a single-local-configuration observation — not production readiness or a cross-account/cross-version guarantee, and it does not establish which credential source was exercised; propagation stays best-effort/bounded/non-fatal, a failure leaves the OpenCode default or manual title, and further live runs remain approval-gated.

**Implemented (shared state-aware transition engine; first exercised live by the completed 2026-09-01 campaign).** `src/eval/scenario-engine.ts` owns the ordered synthetic workflow `read → edit → test → final text` and is consumed by BOTH live evaluators, so their expectations can never drift. ## Request Flow

The intended dependency and data flow is:

```text
Fastify API boundary
  -> authentication and normalized OpenAI request
  -> virtual model resolution and prompt serialization
  -> optional cross-replica rate limit
  -> optional OpenCode thread-reuse lease, or optional idempotency claim/replay
     (mutually exclusive: the combination is rejected before either engages)
  -> capacity acquisition
     (process-local FIFO queue, plus an optional shared cross-replica
      active permit when Phase 4D is enabled; the step does not move)
  -> generation orchestration
  -> typed CollectivIQ adapter and polling
  -> text/tool response parsing
  -> OpenAI object or SSE encoding
```

Observability records metadata around each stage without taking ownership of domain flow or content.

## Boundary Ownership

### Process and composition

- `src/index.ts` is the process entry point: load configuration, construct dependencies, start, and handle signals.
- `src/server.ts` constructs the application without forcing a listening socket, so tests can exercise it in-process.
- Startup fails before listening when required configuration is invalid.

### API boundary

- `src/api/` owns HTTP routing, gateway authentication, body/content-type limits, request IDs, public status/header behavior, and OpenAI-style error envelopes.
- Route handlers delegate use cases; they do not know CollectivIQ wire formats or implement tool parsing.

### OpenAI boundary

- `src/openai/` owns the supported Chat Completions compatibility profile: input schemas, normalization, response objects, and SSE framing.
- Raw public requests must become normalized internal values before they reach generation logic.

### Generation application layer

- `src/generation/` owns orchestration, state transitions, model resolution, polling policy, capacity, cancellation, and deadlines.
- It depends on typed ports and normalized domain values, not Fastify request/reply objects.
- Capacity is acquired before thread creation and released in `finally`-equivalent cleanup.
- It owns the `CapacityController` PORT and the process-local implementation, but not the optional cross-replica one: `src/shared-capacity/` supplies a second implementation of the same port (see its subsection below). Selection happens once in `src/generation/runtime.ts` from validated configuration, so orchestration never branches on capacity mode.

### Upstream boundary

- `src/collectiviq/` is the only code allowed to know `/create_thread`, `/process_message`, `/get_messages`, multipart field names, bearer-header details, or provisional upstream response schemas.
- The adapter returns validated, normalized types and normalized failures.

### OpenCode session-title extension

- `src/opencode/` owns the process-local session-to-upstream-thread correlation (`title-bridge.ts`) that backs the `GET /v1/opencode/session-title` extension route (`src/api/opencode-title-route.ts`, owned by the API boundary). It stores only opaque ids and the upstream thread id under bounded TTL/caps — never a title, prompt, or answer — and is synchronous, bounded, and non-throwing. The route registers one after ANY successful completion that carried a valid session header AND created a thread; it has no notion of title intent, so the plugin's per-request header means title-ineligible sessions can occupy entries the plugin never polls (bounded by first-registration-wins, the caps, and the TTL; a reused turn registers nothing). Spec §25 records that as an accepted residual tradeoff — do not "fix" it here with a title-intent header or a route change.
- `.opencode/plugins/collectiviq-native-title.ts` is the OpenCode-side plugin (not part of the gateway service): it supplies the per-request session identity on every matching foreground request, and separately arms an eligible foreground session once and propagates the CollectivIQ provider-native title back to the OpenCode session by polling that extension endpoint. It is descriptor-safe, best-effort, and process-wide idempotent (see the implementation entry above); it does not know CollectivIQ wire formats and never executes tools. It does not test, trigger, or alter CollectivIQ's provider-side title generation, which stays entirely provider-owned. Detailed behavior belongs to spec §§9.5 and 25 — do not restate it in full here.

### Prompt and tool policy

- `src/prompts/` owns deterministic prompt construction: the versioned full-history conversation/control prompt (`conversation.ts`, `promptMode: "protocol"`), the latest-user-only direct prompt (`direct.ts`, `promptMode: "direct"`), and the model-policy-aware selector (`serializer.ts`) that dispatches on the validated `promptMode` — never a model-id string.
- `src/tools/` owns the emulated protocol envelope, JSON/schema validation, canonicalization, candidate voting, and call-ID generation policy.
- Neither area executes tools.

### Redis substrate

- `src/redis/client.ts` is the ONLY module in the repository allowed to import node-redis. It owns the client, its lifecycle, the connection bounds, and the generic `evalScript` port; it is deliberately ignorant of what any script means.
- `src/idempotency/`, `src/rate-limit/`, `src/shared-capacity/`, and `src/thread-reuse/` are the ONLY features allowed to know their state is stored in Redis, to hold their derived subkeys, to own Lua, and to know their key shapes and wire formats. Nothing above them learns that Redis exists.
- `src/redis/runtime.ts` is the Redis composition root and creates EXACTLY ONE client per process, shared by every enabled feature — now FOUR of them — with one reconnect policy, one readiness probe, and one shutdown close. Never add a second client. It is intentionally not re-exported from `src/redis/index.ts`, because it depends on the feature boundaries; keeping it out of the barrel keeps the dependency direction one-way (features → substrate).
- The substrate is TOTAL: `evalScript` returns `null` for every failure rather than throwing, so a feature can always fail closed without inspecting a thrown value. Preserve that.
- Construction must stay socket-free: only the process composition root connects and closes.

### Idempotency boundary

- `src/idempotency/` owns the derived idempotency subkeys, the record/payload wire formats, and its five Lua scripts. It exposes a narrow port (`store.ts`) plus a coordinator that returns discriminated outcomes.
- It depends only on normalized values, generic ports (`Clock`, `Sleeper`, `RandomFn`), and the Redis substrate; it must not import from `src/api/` or take a Fastify request/reply. Public statuses, envelopes, and headers stay owned by the API boundary.
- Claim before capacity; transition to `processing` after capacity and before thread creation; commit `final` before the non-streamed response body and before any SSE content or terminal frame (SSE headers and the assistant-role opener precede it by design, so a late failure there is an SSE error record rather than an HTTP status); leave `ambiguous` on any failure at or after `processing`. Never add a `create_thread`/`process_message` retry.
- Its Lua, derivation constants, and record/payload formats are a stored-data contract. Changing them re-keys or invalidates live records; treat any edit as a migration, not a refactor.

### Rate-limit boundary

- `src/rate-limit/` owns the GCRA arithmetic, its own derived subkey, its single Lua decision script, and the `<prefix>:rate:<HMAC>` key shape. It exposes only the closed `RateLimitDecision` union and the `RateLimiter` port; the API boundary owns every public status, header, and envelope.
- Its keyring shares NO code with `src/idempotency/keyring.ts` — the length-framing helper is duplicated on purpose. Do not "de-duplicate" it: a change there must never be able to re-key stored idempotency records.
- One request produces exactly ONE atomic server-side decision. Never introduce a read-then-write, a local counter, or a Node clock: time comes from Redis `TIME` so replica clock drift cannot corrupt a shared quota.
- Every unusable stored value fails CLOSED as `unavailable`; the script never resets or repairs state, and the caller never allows on failure.
- Meter after all input validation and prompt preparation, and before the idempotency claim, capacity, any SSE header, and any upstream call. Never refund a consumed unit. Keep it scoped to the completion route.

### Shared-capacity boundary

- `src/shared-capacity/` owns the derived capacity subkey, the versioned `version | owner | scope` ZSET member format, its two Lua scripts, and the ONE namespace-level `<prefix>:capacity:<HMAC>` registry key. It implements the SAME `CapacityController` port as `src/generation/capacity.ts`, so nothing above it knows which controller it holds; the API boundary owns every public status, header, and envelope. Specification §19.2 owns the normative contract.
- Its keyring shares NO code with `src/idempotency/keyring.ts`, `src/rate-limit/keyring.ts`, or `src/thread-reuse/keyring.ts` — the length-framing helper is duplicated on purpose. Do not "de-duplicate" it: a change here must never be able to re-key another feature's stored state.
- Its Lua, derivation constants, and member format are a stored-data contract. Changing them invalidates live permits; treat any edit as a migration, not a refactor.
- Only the two ACTIVE limits are shared. `MAX_QUEUED_REQUESTS`, `MAX_QUEUE_WAIT_MS`, local FIFO order, and per-key bypass stay PER REPLICA, and no cross-replica queue fairness is promised — replicas compete for the shared budget and a busy replica's queue does not yield to an idle one. Do not move queueing into Redis to "fix" that.
- There is deliberately no per-scope registry key: the global limit must be counted across all gateway keys, which a per-scope key could not do atomically. Per-key occupancy is counted from the scope carried inside each member.
- A claim is a BATCH and there is at most ONE claim in flight per process. Batching is what lets the server apply the per-key limit across several waiters atomically; the reply names the granted OWNER TOKENS, never a count, because per-key bypass means the granted set is not a prefix of the candidates. Never replace it with a sequence of single claims or a local counter.
- Every mutation is ONE atomic Lua script over a COMPLETELY validated registry; there is no read-then-write anywhere. Cardinality is checked before any member is materialized, and a wrong type, over-cardinality registry, malformed member or score, or duplicated owner token is `corrupt` and leaves the registry byte-for-byte untouched. The registry key always expires at its latest member deadline and is deleted when empty, so even corrupt state self-heals within one lease window without the gateway pruning it.
- The lease is a CRASH REAPER, not a liveness mechanism: it is derived from the holder's own request deadline plus a fixed margin and stamped from Redis `TIME`, never a Node clock. There is deliberately NO heartbeat and NO renewal script — do not add one, and do not let a lease be chosen by a caller.
- Being at the cluster limit leaves waiters QUEUED; only the local queue bounds and closed admission produce a `429`. An unavailable, corrupt, or ambiguous claim is `503 capacity_unavailable` and is NEVER retried or compensated, because the gateway cannot know whether the mutation applied: a retry could double-count a permit it already holds and a speculative release could remove one another replica now holds. Any member that WAS added stays an orphan bounded by its own lease. Only the full-capacity outcome is retried, under a bounded jittered backoff.
- A confirmed grant is never dropped: if a waiter departs while the claim is in flight and Redis then confirms its grant, the permit is released immediately. Release is issued WITHOUT the request's abort signal, because a released permit must be given back even when its request was cancelled, and it is idempotent — an already-absent member reports `ok`.
- Keep the capacity step where it is (after the rate-limit decision, the reuse lease, and the idempotency claim; before the `processing` transition and any upstream call). Enabling this feature must move nothing else in the admission order.

### Thread-reuse boundary

- `src/thread-reuse/` owns the four derived reuse subkeys, the mapping-identity framing, the five-state record wire format, its nine Lua scripts, and the `<prefix>:reuse:<HMAC>` key shape. It exposes a narrow port (`store.ts`) plus a coordinator that returns discriminated outcomes; the API boundary owns every public status, header, and envelope. Specification §5.1.1 owns the normative contract.
- Its keyring and crypto share NO code with `src/idempotency/` or `src/rate-limit/`. The duplication is deliberate for the same reason as the rate limiter's: a change here must never be able to re-key or invalidate stored records of another feature.
- The state machine is single-key and every mutation is ONE atomic Lua script; there is no read-then-write anywhere. The lease deadline lives INSIDE the record and is stamped and compared against Redis `TIME`, never a Node clock, because Redis `PX` carries the MAPPING lifetime instead — a record must survive its lease so an expired `processing` record can become `ambiguous` rather than vanish.
- Take the lease after the rate-limit decision and before capacity. Bind a created thread while still `reserved`; move to `processing` immediately before `process_message`; finalize through the acknowledgement-safe `processing → committed → active` sequence, where the COMMIT must be locally acknowledged before the JSON body or any SSE content/terminal frame is authorized; restore or delete on a proven pre-submit failure. A blocked post-submit outcome is `ambiguous`, OR a bounded, non-acquirable `committed` when the commit succeeded but activation is unconfirmed; an activation that finds the mapping genuinely absent atomically tombstones it as `ambiguous`. Never add a `create_thread`/`process_message` retry, and never silently create a replacement thread on failure. Specification §5.1.1 owns the full state machine.
- Its Lua, derivation constants, and record format are a stored-data contract. Changing them re-keys or invalidates live mappings; treat any edit as a migration, not a refactor.
- Eligibility is narrow by design (`promptMode: "direct"` + `toolMode: "disabled"` + a valid session header + the feature enabled). Do not broaden it to protocol or tool requests, and do not make it a default.

### Cross-cutting support

- `src/config/` owns validation and loading, not mutable global state.
- `src/observability/` owns safe logging/metrics/tracing APIs and redaction defaults. `labels.ts` is the ONLY place a telemetry dimension may be defined, and every mapping into it is total, so an unrecognized value collapses to a fixed fallback instead of creating a series. Only `metrics.ts` may import `@prometheus-io/client` (the maintained successor to the deprecated `prom-client`) and only `tracing.ts` may import any `@opentelemetry/*` package; nothing above the boundary learns which library is in use. Both ports expose `enabled`, and every caller must branch on it: a disabled gateway builds no span options, no observation samples, and no closures, reads no telemetry clock, and calls neither port. Both ports are TOTAL and non-throwing — telemetry is best-effort and must never change admission order, status codes, or response bodies, which is the deliberate opposite of the fail-closed Redis features. Assign each metric and span exactly one writer; a second writer for an existing signal is a duplicate-counting bug.
- `src/shared/` is for small cohesive primitives such as IDs, abort-aware deadlines, and redaction helpers. It must not become a dumping ground.

## Core Domain Types

Prefer explicit types for:

- normalized chat requests and messages;
- virtual model execution policy;
- request context, state, and terminal failure category;
- upstream adapter inputs/results/capabilities;
- parsed text versus parsed tool-call generations;
- public error codes and response encoding inputs.

Keep raw public and upstream payload types at their boundaries. Do not pass arbitrary objects or framework request types through the service.

## State and Lifecycle Invariants

- One public completion maps to one new upstream thread. The single exception is optional OpenCode thread reuse (spec §5.1.1, off by default): an eligible direct-prompt, tool-free request that continues its session's leased thread creates none. It still submits exactly once.
- The full conversation is serialized on every completion request for `promptMode: "protocol"` models (the default). The `promptMode: "direct"` compatibility profile is the one exception — it serializes only the latest user message and intentionally drops the rest (spec §8.4.1) — and must not be generalized to protocol models.
- A concurrency permit covers thread creation through parsing and cleanup. The two ACTIVE limits it enforces are per replica by default and cluster-wide when the optional Phase 4D layer is enabled (spec §19.2); the queue bounds are per replica either way, and the permit's position in the admission order is identical in both modes.
- Client abort and total deadline share a cancellation path that stops polling and releases resources.
- A public response is encoded only from a validated parsed generation.
- State-transition instrumentation never includes prompt or response content.
- Upstream event streaming remains out of scope until the prerequisites in the specification are verified. Thread reuse is now implemented as an optional, off-by-default, fail-closed feature (spec §5.1.1) that deliberately does NOT depend on the unverified ordering/pagination/cleanup prerequisites: every completion's poll accepts only a message whose `combined_run_id` equals its own submission's, and times out rather than returning older content. It is not production ready and must not become a default.

## Change Guidance

- Add behavior to the component that owns the policy; do not shortcut boundaries for convenience.
- If a new upstream field is useful, validate it in the adapter before exposing a normalized field.
- If a public compatibility behavior changes, update schemas, encoders, compatibility tests, and documentation together.
- If orchestration changes, test success, timeout, cancellation, and cleanup paths.
- Avoid speculative interfaces for unverified CollectivIQ features. Represent capability uncertainty explicitly.
- Keep components independently testable through dependency injection or narrow constructor/factory inputs.
