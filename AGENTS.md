## Repository Facts

- The project is the CollectivIQ OpenAI-Compatible Gateway: a local or privately hosted HTTP service between OpenCode and CollectivIQ.
- The compatibility target is the bounded OpenAI Chat Completions profile needed by `@ai-sdk/openai-compatible`, not the full OpenAI API.
- The reference stack is current supported Node.js LTS, strict TypeScript, Fastify, native `fetch` or Undici, schema validation, Pino, Prometheus-compatible metrics, Vitest, npm, and Docker.
- Each completion is stateless from the public API's perspective and creates exactly one new CollectivIQ thread, with ONE optional, off-by-default exception: Phase 5A OpenCode thread reuse (see its entry below and specification section 5.1.1).
- Only the typed CollectivIQ adapter may know upstream endpoint paths and wire schemas.
- The gateway translates tool definitions and model-generated requests but never executes OpenCode tools.
- Input is text-only in the initial release. Responses support non-streamed output and buffered synthetic SSE streaming.
- Prompt content, source code, file paths, tool arguments/results, and model answers are neither logged nor retained by default.
- Emulated tool calling is **supported opt-in beta**: all numerical release gates in `.agent/docs/tech-software-spec.md` section 30 pass (completed 2026-09-01 campaign), and on that evidence it graduated from experimental to supported opt-in beta. It stays **non-default and OpenCode permission-gated**; beta is not production readiness, repeatability, or a cross-account/cross-version guarantee, and default enablement is a separate decision after the Phase 4 controls. Section 30 owns the graduation decision — summarize it elsewhere, never restate its evidence.
- **Phase 4A (optional Redis-backed cross-replica idempotency) is implemented and is OFF BY DEFAULT.** With a blank/absent `REDIS_URL` the gateway behaves exactly as before for unkeyed requests and never contacts Redis. `POST /v1/chat/completions` accepts one optional `Idempotency-Key` header (single occurrence, 1–255 bytes of visible ASCII, never logged/reflected/stored — only a keyed HMAC reaches Redis). A supplied key REQUIRES configured, healthy Redis or the request fails closed with `503 idempotency_unavailable` + `Retry-After: 2` before any completion work; an invalid header or unfingerprintable body is `400 invalid_idempotency_key`; the same scoped key with a different body is `409 idempotency_key_conflict`. "Same body" is the canonical full parsed JSON (key order and whitespace insignificant, array order significant, EVERY submitted field included — even tolerated-and-discarded tool metadata). The boundary lives in `src/idempotency/`; one 32-byte `IDEMPOTENCY_ENCRYPTION_KEY` is expanded with HKDF-SHA-256 into three domain-separated subkeys, cached final responses are AES-256-GCM encrypted with a fresh nonce and version/storage-key/fingerprint-bound associated data, and the Redis key is an HMAC of namespace + a stable ordering-independent gateway-key scope + the client key. Claim and every compare-and-transition are atomic Lua; the claim precedes capacity, `reserved → processing` runs after capacity and before `create_thread`, `processing → final` must commit before the non-streamed response body and before any SSE content/terminal frame (SSE headers and the assistant-role opener precede it by design, so a late failure there is an SSE error record rather than an HTTP status), and any failure at or after `processing` stays `ambiguous` for the TTL. **No `create_thread`/`process_message` retry was added, capacity was left entirely PROCESS-LOCAL by this phase, and no live CollectivIQ call was made or required.** (Capacity is still process-local by default; the optional, off-by-default Phase 4D layer below makes only the two ACTIVE limits cluster-wide when explicitly enabled, and Phase 4A neither depends on it nor changes with it.) Protection is bounded to the configured TTL; CollectivIQ's own POST-idempotency semantics remain unknown. **Specification section 18.1 owns the normative contract — summarize it elsewhere, never restate it.** Still outstanding in Phase 4: load testing, the broader security review, dependency scanning, and backup/release procedures/runbooks (metrics and tracing are implemented — see the Phase 4C entry below — and shared cross-replica capacity accounting is implemented per the Phase 4D entry below).
- **Phase 4B (optional Redis-backed cross-replica per-gateway-key rate limiting for `POST /v1/chat/completions`) is implemented and is OFF BY DEFAULT.** With `RATE_LIMIT_ENABLED=false` no limiter is built, no scope is derived, and no Redis rate-limit operation occurs; enabling it REQUIRES a valid `REDIS_URL` (which already requires `IDEMPOTENCY_ENCRYPTION_KEY`) and adds NO new secret. It is one atomic GCRA Lua decision per request against Redis's own `TIME`, gated after all input validation and prompt preparation and before the thread-reuse lease, the idempotency claim, capacity, any SSE header, and any upstream call; it fails CLOSED (`503 rate_limit_unavailable` + `Retry-After: 2`) on any unusable dependency or corrupt state and returns `429 gateway_rate_limit_exceeded` with a limiter-computed `Retry-After` when the quota is spent. The rate-limit subkey is expanded from the shared master key under a SEPARATE HKDF domain, so a gateway key's rate-limit scope differs from its idempotency scope, and Redis holds only a bounded per-scope integer timestamp under a `:rate:` category. Phase 4B also introduces `src/redis/`, the shared substrate whose `client.ts` is the only module importing node-redis and whose `runtime.ts` creates EXACTLY ONE client per process for every enabled Redis-backed feature — idempotency, rate limiting, (since Phase 4D) shared capacity, and (since Phase 5A) thread reuse — with one readiness probe and one shutdown close; the idempotency Lua, constants, and record formats are byte-for-byte unchanged and existing records stay readable. Capacity was left entirely PROCESS-LOCAL by this phase (it is still process-local by default, and only the optional, off-by-default Phase 4D layer below makes the two ACTIVE limits cluster-wide when explicitly enabled), no dependency or lockfile entry changed, and no live CollectivIQ call was made or required. - **Phase 4C (optional bounded Prometheus metrics and opt-in OpenTelemetry tracing) is implemented and BOTH are OFF BY DEFAULT.** "Off" means STRUCTURALLY inert: both ports expose an `enabled` flag fixed at construction and EVERY call site branches on it, so with `METRICS_ENABLED=false` and `TRACING_ENABLED=false` there is no Prometheus registry, no `GET /metrics` route (the endpoint returns the framework `404`), no tracer provider, no exporter, no timer, no socket, no span options or observation samples, no per-request closures, no telemetry clock read, no bound capacity source, no decorated adapter, no root telemetry hook, and no call into either port — at SHUTDOWN too, where the telemetry close step skips `tracing.shutdown()` outright rather than delegating to a no-op. The honest residual cost is ONE FIXED BOOLEAN CHECK per call site, never "zero instructions". The mechanism is NULLABILITY, not no-op objects: `request.telemetry` is `null` when disabled (there is deliberately no shared no-op handle, which would let auth/model/error paths keep invoking methods), and span/stream helpers are `null` rather than no-op functions so optional invocation short-circuits WITHOUT building their attribute objects. The no-op port implementations stay total as defence in depth but are NOT the mechanism — never add a call site that skips the branch, and never reintroduce a no-op handle. Four validated variables were added (`METRICS_ENABLED`, `TRACING_ENABLED`, `TRACING_OTLP_ENDPOINT` — a canonical absolute http(s) traces URL, REQUIRED when tracing is enabled and validated whenever present — and `TRACING_SAMPLE_RATIO`, a plain decimal in `[0, 1]`), plus five exactly-pinned dependencies (`@prometheus-io/client` — the maintained successor to the DEPRECATED `prom-client`, which must not be reintroduced — `@opentelemetry/api`, `@opentelemetry/sdk-trace-node`, `@opentelemetry/exporter-trace-otlp-http`, `@opentelemetry/resources`) and deliberately NO automatic-instrumentation package, which would capture URLs, headers, and uncontrolled attributes. Neither feature needs Redis, a credential, or any other feature. Facts an agent must not get wrong: **cardinality IS the privacy boundary** — every label and span attribute is a member of a frozen vocabulary in `src/observability/labels.ts` or a CONFIGURED virtual-model id, re-checked at write time, with an unrecognized value collapsing to a fixed fallback (metrics) or being dropped (spans), so no prompt, answer, path, URL, tool name/argument/result, credential, gateway key/scope, idempotency key, session/thread/request/tool-call id, or exception text can reach either signal and the endpoint label is always a route TEMPLATE; **every signal has exactly ONE writer** (spec §23.2 owns the table) so a second writer is a duplicate-counting bug, not extra coverage; **request settlement reads the raw response's `finish`/`close` behind a one-shot guard rather than Fastify's `onResponse`**, because a hijacked SSE reply may be force-destroyed without ever being "sent", which is what makes JSON and SSE each settle exactly once; **tracing uses manual spans with EXPLICIT parentage from `ROOT_CONTEXT`** and never calls `provider.register()`, never consults `context.active()`, never calls `recordException`, and never propagates a trace header to CollectivIQ; **`GET /metrics` is unauthenticated by design** when enabled (a scrape credential would be a second secret and the process cannot verify its interface is private), so operators MUST isolate it by loopback/private network/firewall; and **telemetry is best-effort, never a correctness control** — every observation is total and non-throwing, admission order is untouched, and an enabled-but-unwired tracer degrades to no traces rather than failing requests, which is the deliberate opposite of the fail-closed Redis features. `buildServer` may build the pure, socket-free registry; only the process root constructs the exporter and closes it, after Redis, in the same bounded dependency-close step under a fixed 2 s budget. `PollOutcome` now carries `pollCount`. No live collector, Redis, OpenCode, or CollectivIQ call was made or required, and admission, SSE, cancellation, idempotency, thread-reuse, and shutdown semantics are unchanged. **Specification sections 23.2 and 23.3 own the normative contract — summarize them elsewhere, never restate them.** Implementing this does NOT close Phase 4: load testing, the broader security review, dependency scanning, and backup/release procedures/runbooks remain outstanding (shared cross-replica capacity accounting is now implemented — see the Phase 4D entry below).
- **Phase 4D (optional Redis-backed cross-replica ACTIVE-capacity accounting for `POST /v1/chat/completions`) is implemented and is OFF BY DEFAULT.** With `SHARED_CAPACITY_ENABLED=false` (the default) no capacity scope is derived, no coordinator is built, and no Redis capacity operation ever occurs; admission is byte-for-byte the pre-Phase-4D process-local controller. ONE validated variable was added — `SHARED_CAPACITY_ENABLED`, strictly parsed (`"true"`/`"false"` only), whose present-but-invalid value is a value-free `ConfigError` even while the feature is disabled. Enabling it REQUIRES a valid `REDIS_URL` (which by the existing Phase 4A rule requires `IDEMPOTENCY_ENCRYPTION_KEY`); enabling it without an endpoint is a value-free startup error, never a silent downgrade. It adds NO new secret, NO new dependency, NO lockfile change, and NO new tuning variable: enabling it REINTERPRETS the existing `MAX_CONCURRENT_REQUESTS` and `MAX_CONCURRENT_REQUESTS_PER_KEY` as **cluster-wide** active limits, while `MAX_QUEUED_REQUESTS` and `MAX_QUEUE_WAIT_MS` remain **per replica**. Only the two ACTIVE permits are shared: queues stay process-local, local FIFO order and per-key bypass are preserved, and **no cross-replica queue fairness is promised** — replicas compete for the shared budget and a busy replica's queue does not yield to an idle one. Facts an agent must not get wrong: state is ONE namespace-level Redis lease registry (a ZSET) under a `:capacity:` key category holding only a version, a random 128-bit owner token, and an opaque per-gateway-key capacity scope, with an integer lease deadline stamped from Redis's own `TIME` — never a request, thread, session, model, tool, prompt, answer, credential, raw gateway key, or process-local `k<index>` identity; the boundary lives in `src/shared-capacity/`, composes over the ONE shared Redis client, derives a capacity-specific HKDF/HMAC domain (independent salt, `info`, and domain tags) from the shared `IDEMPOTENCY_ENCRYPTION_KEY`, and adds a **fifth** opaque gateway-key auth identity `capacityScopeId` (the **fourth** cross-replica scope, after idempotency, rate limit, and thread reuse) that is stable across replicas and independent of gateway-key ORDER while the process-local `k<index>` is never written to Redis; there are exactly TWO atomic Lua scripts (`claimBatch`, `release`) and deliberately **NO heartbeat and NO renewal script**, because the lease is a crash reaper derived from the holder's own request deadline plus a fixed margin, so a live request's permit cannot expire mid-completion; one process-local single-flight batch scheduler keeps at most one Redis claim in flight per process, with batches built in local FIFO order; being at the cluster limit leaves waiters QUEUED (ordinary backpressure), not rejected; it fails CLOSED — an unavailable, corrupt, or ambiguous claim is never retried and never compensated, the request fails closed, any member that was added is an orphan bounded by its own lease, and corrupt or oversized state is left byte-for-byte untouched; and the registry key expires at the latest active lease and is deleted when empty. The capacity step keeps its EXISTING position in the admission order, so nothing else moved: auth → validation/model/tools → idempotency header+fingerprint → reuse eligibility → prompt preparation → rate limit → reuse lease → idempotency claim/wait/replay → process-local FIFO queue + shared active permit → reuse/idempotency `processing` transition → create/continue thread → submit once → poll → release permit → encode. Consequences worth remembering: rate-limit quota is spent before capacity and never refunded; idempotency waiters and replays take no capacity; a capacity failure before `processing` releases/restores the idempotency claim and the reuse lease; on the SSE transport capacity is reached after the headers and the assistant-role opener, so a capacity failure there is a safe SSE error record and NOT a new HTTP status; and **no `create_thread`/`process_message` retry was added**. Public errors: queue full, queue-wait timeout, and closed admission keep the existing `429 gateway_capacity_exceeded` + `Retry-After: 5` in BOTH capacity modes, and the NEW `503 capacity_unavailable` (`type: server_error`, `param: null`, `Retry-After: 2`) covers an unusable Redis, corrupt or ambiguous state, or an enabled-but-unwired instance — distinct from the `429` because one says the cluster is busy and the other says the gateway cannot tell. The only observability change is the added closed error category `capacity_unavailable`; **no new metric or span name**. Operationally: enablement or a change to the capacity limits requires a **coordinated drain/restart** and mixed local/shared rolling operation is **unsupported**; every replica must share an IDENTICAL Redis endpoint, `IDEMPOTENCY_ENCRYPTION_KEY`, `REDIS_KEY_PREFIX`, `COLLECTIVIQ_GATEWAY_KEYS` set, `SHARED_CAPACITY_ENABLED` value, and capacity limits, or the budget is not the single shared budget it appears to be; `maxmemory-policy noeviction` remains **mandatory** (the §18.1 requirement applies here too) because an evicted or lost registry key forgets live permits and can briefly OVER-admit undetectably, as can a Redis restart, while Redis persistence and backups remain intentionally unnecessary; a failed or unacknowledged release conservatively UNDER-admits this replica until the lease expires and never changes an already successful response; an ambiguous claim can leave an orphan lease invisible to local gauges; the active/queued gauges remain **per instance**, so Prometheus aggregation across replicas can approximate live cluster occupancy but cannot see orphan leases and no replica can observe cluster occupancy directly; and enabling the feature deliberately trades availability for correctness on the completion path, exactly like Phase 4B. No live CollectivIQ, OpenCode, or OTLP call was made or required. Do not claim a command exists or passed when it was unavailable. Do not install dependencies, regenerate a lockfile broadly, or choose package versions as a side effect of unrelated work.

## Architectural Invariants

- Keep the public API stateless. The one exception is the optional, off-by-default OpenCode thread reuse of specification section 5.1.1: it is narrow (direct-prompt, tool-free, valid session header, explicitly enabled), fail-closed, and deliberately does NOT depend on the still-unmet correlation, cleanup, and ordering prerequisites. Do not broaden it, do not make it a default, and do not introduce any other form of upstream-thread reuse until those prerequisites are met.
- Preserve full ordered conversation history and declared roles in the versioned JSON envelope for `promptMode: "protocol"` models (the default). The narrowly scoped `promptMode: "direct"` profile is the one intentional exception: it submits only the latest normalized user message and deliberately drops the protocol wrapper, system/developer instructions, assistant history, and earlier user turns (spec §8.4.1). Do not extend that lossy behavior to protocol models, and select prompt behavior from the validated `promptMode`, never a model-id string.
- Keep upstream schemas and endpoint knowledge inside the CollectivIQ adapter.
- Treat every upstream response as untrusted and validate it before use.
- Never execute tools in the gateway.
- Polling remains authoritative until request-scoped upstream event correlation is verified.
- Do not automatically retry `create_thread` or `process_message` without proven idempotency.
- Acquire concurrency capacity before creating an upstream thread, and release it on every exit path.
- Keep Redis-backed cross-replica capacity accounting OPTIONAL and fail-closed, and keep it to the two ACTIVE permits only: queues, local FIFO order, and per-key bypass stay per replica, and no cross-replica queue fairness is promised. The capacity step keeps its EXISTING position in the admission order — after the rate-limit decision, the reuse lease, and the idempotency claim, and before the `processing` transition and any upstream call — so enabling the feature must move nothing else. Every mutation is one atomic Lua script over a completely validated registry; the lease deadline comes from Redis `TIME` and the holder's own request deadline plus a fixed margin, so there is deliberately NO heartbeat and NO renewal. Being at the cluster limit leaves waiters QUEUED (`429` still comes only from the local queue bounds and closed admission); an unavailable, corrupt, or ambiguous claim is `503 capacity_unavailable` and is NEVER retried, compensated, or repaired — a member that was added stays an orphan bounded by its own lease. Never admit on an unusable dependency, never derive a lease from a Node clock, and keep the capacity key domain cryptographically separate from every idempotency, rate-limit, and thread-reuse subkey.
- Keep Redis-backed idempotency OPTIONAL and fail-closed: create the claim atomically before capacity or upstream work, move `reserved → processing` after capacity and before `create_thread`, commit `processing → final` before the non-streamed response body and before any SSE content or terminal frame (SSE headers and the role opener precede it by design), and leave `ambiguous` (blocked for the TTL) on any failure at or after `processing`. Every mutation is atomic Lua, never a GET-then-SET.
- `src/redis/client.ts` is the ONLY module that may import node-redis, and `src/redis/runtime.ts` is the only place that creates a client — exactly one per process, shared by every enabled feature. Only `src/idempotency/`, `src/rate-limit/`, `src/shared-capacity/`, and `src/thread-reuse/` may know their state lives in Redis or own Lua; nothing above them learns Redis exists.
- Keep Redis-backed OpenCode thread reuse OPTIONAL, narrow, and fail-closed: take the session lease after the rate-limit decision and before capacity, bind a created thread while still `reserved`, mark `processing` immediately before `process_message`, finalize through the acknowledgement-safe `processing → committed → active` sequence with the commit LOCALLY acknowledged before any JSON body or SSE content/terminal frame is authorized, and restore or delete on a proven pre-submit failure. A post-submit failure does not universally store `ambiguous`: an uncertain or unaccounted-for possible submit leaves `ambiguous`, an acknowledged commit whose activation stays unconfirmed may truthfully remain in the bounded, non-acquirable `committed` state, and an activation that finds the mapping genuinely ABSENT atomically persists an `ambiguous` tombstone. Every one of those outcomes blocks the session; none silently creates a replacement thread. Every mutation is atomic Lua over a COMPLETELY validated record, the lease deadline and every state's Redis lifetime come from Redis `TIME` and the stored state, `committed` is never acquirable, and selection is by `combined_run_id` so an earlier turn's answer can never be returned. Never combine it with idempotency and never silently create a replacement thread.
- Keep Redis-backed rate limiting OPTIONAL and fail-closed: one atomic GCRA decision per request against Redis's own `TIME` (never a Node clock), metered after all input validation and prompt preparation and before the idempotency claim, capacity, any SSE header, and any upstream call. Never refund a consumed unit, never allow on an unusable dependency or corrupt stored value, and keep the rate-limit key domain cryptographically separate from every idempotency subkey.
- Propagate client cancellation through pending upstream work and stop polling promptly.
- Return OpenAI-style public errors; never expose raw production upstream bodies.
- Do not present estimated token counts as exact usage.
- Do not broaden compatibility or enable opt-in beta tool mode by default without the corresponding tests, documentation, release evidence, and the separate default-enablement decision recorded in specification section 30.

## Critical Risk Index

Read the routed security and domain instructions before changing:

- credential handling, authentication, gateway binding, TLS assumptions, or metrics exposure;
- prompt serialization, role precedence, boundary generation, or content logging;
- tool parsing, JSON Schema validation, tool-choice enforcement, or fallback voting;
- upstream retries, timeouts, polling completion, duplicate-message selection, or cancellation;
- request/body/prompt/tool/upstream size limits, queues, concurrency, or rate limits;
- Redis idempotency, response caching, retention, cross-replica state, session-to-thread mappings, or cross-replica active-capacity permits;
- SSE framing, keep-alives, terminal chunks, or disconnect handling;
- error/status mappings and any raw upstream diagnostic data.

## Approval Required

Ask for explicit user approval before initiating:

- destructive file operations, mass deletion, recursive moves, overwrite scripts, or cleanup commands;
- Git history changes, force pushes, shared-branch rebases, commits, pushes, tags, releases, or PR publication unless explicitly requested;
- deployment, package publishing, infrastructure mutation, secret-store changes, or other external writes;
- reading, printing, copying, rotating, or modifying real credentials or sensitive prompt/response data;
- major dependency upgrades, package-manager migrations, or broad lockfile regeneration outside the task;
- live CollectivIQ probes that transmit repository content or may create material cost/thread volume;
- enabling content logging, persistent prompt/response storage, opt-in beta tool mode, or OpenCode thread reuse in a production configuration;
- large mechanical rewrites, generated-code refreshes, or formatting sweeps across many files.

State the exact action, why it is needed, what it can change or expose, and a safer alternative when one exists.

## Security and Privacy Musts

- Keep the upstream credentials — `COLLECTIVIQ_API_KEY` (bearer mode) or `COLLECTIVIQ_USERNAME`/`COLLECTIVIQ_PASSWORD` (password mode) — separate from gateway client keys, and redact all of them everywhere.
- Never commit real secrets or include them in commands, logs, fixtures, examples, errors, traces, snapshots, or session notes.
- Keep production content logging off. Development content logging requires both the explicit development-only switches and a prominent warning.
- Default binding is loopback. Non-loopback exposure requires explicit configuration plus authentication and deployment controls.
- Validate and bound request bodies, prompts, tool collections/schemas/arguments, upstream responses, queues, concurrency, and durations.
- Hash correlation identities only when needed; do not use prompt-derived permanent identifiers across trust boundaries.
- Sanitize every live upstream fixture before committing it.
- Treat prompt injection as an inherent trust-boundary risk, not something JSON delimiters eliminate.
- Preserve the default no-content-retention behavior; short-lived caches require an explicit design and security review.

Use `.agent/instructions/security.md` for the complete task checklist.
